BACKGROUND / PROBLEM STATEMENT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The Agriculture Rover was originally controlled by a BeagleBone Black (BBB)
running Debian Linux with Python 3.11. In field conditions (high ambient
temperatures), the BBB would freeze and become unresponsive, making the rover
unsafe to operate.

Decision: Replace the BBB with an STM32F411CEU6 (Black Pill) — a Cortex-M4
microcontroller running at 100 MHz, far more thermally robust, with no OS
overhead, deterministic real-time behaviour, and low power draw.

This log documents every step taken from initial code understanding through
hardware bring-up, module implementation, debugging, and first successful
hardware tests.

  TIM5             | (internal) | 32-bit us counter for delays & timestamps
  TIM4             | (internal) | 20 Hz main loop timer (50 ms period)

--- Encoder Strategy Decision ---

  Considered three approaches:
    1. Encoder Mode (counting edges) — rejected: at 20 RPM wheel shaft,
       only ~40 counts per 50 ms loop cycle → too coarse for PID.
    2. Input Capture — selected: measures period between pulses; gives
       sub-0.1 RPM resolution regardless of wheel speed.
    3. Interrupt-based — similar to input capture but simpler.

  Final choice: TIM2/TIM3 in Combined Encoder Mode TI1+TI2 (quadrature),
  with TIM3 overflow interrupt to handle slow/stopped detection. RPM
  computed from edge period measured against TIM5 microsecond counter.

  Encoder filter set to value 9 in CubeMX to debounce 4.2 kΩ pull-up
  encoder signals (removes switch bounce / EMI spikes in agricultural env).
  External pull-ups confirmed: 4.2 kΩ on each phase to 3.3 V (user-provided).

--- I2C Configuration ---

  I2C1 for MCP4725 DACs (PB6/PB7).
  Pull-up resistors on PCB: 4.7 kΩ to 3.3 V.
  Initial setting: 400 kHz (Fast Mode).
  LATER CHANGED to 100 kHz — see Section 5 for reason.

--- CubeMX Settings Applied by User ---

  TIM2, TIM3 : Encoder Mode, TI1 Input Filter = 9
  TIM5       : Internal Clock, 32-bit counter, prescaler = 99 → 1 MHz (1 µs)
  TIM4       : Internal Clock, prescaler gives 20 Hz period
  USART1     : 115200 baud, 8N1, DMA RX enabled (added later)
  I2C1       : Standard mode 100 kHz (corrected from 400 kHz)
  GPIO       : Contactor, Rev L/R, Brake L/R as Push-Pull Output
  DMA2       : Stream 2, Channel 4 — USART1 RX (added in second pass)

SECTION 3 — STM32 MODULE IMPLEMENTATION (All Modules Written)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

All source and header files created under /home/suyash/stm/Rover/Core/:

--- 3.1  config.h  (Core/Inc/config.h) ---

  Central configuration header — mirrors BBB config.py in C #defines.
  Contains: geometry, motor/gearbox params, encoder constants, control
  tuning (DEADBAND, EPSILON, MIN_RATIO, SPOT_RPM), timing constants,
  DAC addresses (0x60 / 0x61), iBUS protocol constants, channel map,
  switch thresholds (SWC/SWD/SWB), and motor direction multipliers.

  Key constants:
    DAC_LEFT_ADDR   0x61
    DAC_RIGHT_ADDR  0x60
    DAC_MAX         4095
    IBUS_FRAME_LEN  32
    IBUS_CH_X       0
    IBUS_CH_Y       1
    IBUS_CH_SWC     4
    IBUS_CH_SWD     5
    IBUS_CH_SWB     6
    RC_TIMEOUT_US   400000  (400 ms no-frame → RC lost)
    LOOP_HZ         20
    LOOP_PERIOD_US  50000

--- 3.2  motor.c / motor.h  (Core/Src/motor.c, Core/Inc/motor.h) ---

  Replaces BBB motor_controller.py + smbus2 + Adafruit_BBIO.

  Functions implemented:
    Motor_Init()          — Set all GPIOs low, DAC to zero, clear state
    Motor_Energize()      — Pull Contactor GPIO high, 500 ms settle delay
    Motor_Deenergize()    — Zero DACs, pull Contactor GPIO low
    Motor_SetSpeeds()     — Direction change detection, GPIO toggling,
                            brake release, DAC write with 20 ms sequence delay
    Motor_Brake()         — Zero DACs, assert brake GPIOs
    Motor_Stop()          — Zero DACs, release brake GPIOs (coast)
    Motor_BrakeThenReverse() — 500 ms brake → call SetSpeeds for reverse
    Motor_IsArmed()       — Returns armed state
    Motor_WasReversing()  — Returns reversal state flag

  _WriteDac() — Private I2C helper:
    Sends MCP4725 "Write DAC Register" command (3 bytes):
      buf[0] = 0x40  (command byte, no EEPROM write)
      buf[1] = D[11:4]
      buf[2] = D[3:0] << 4
    Using HAL_I2C_Master_Transmit, addr << 1 (7-bit shift), 50 ms timeout.

  _DelayUs() — Busy-wait using TIM5 CNT register (1 µs resolution).

--- 3.3  encoder.c / encoder.h  (Core/Src/encoder.c, Core/Inc/encoder.h) ---

  Replaces BBB eQEP counter reading.

  Method: Period-based RPM measurement using TIM2 (left) and TIM3 (right)
  in Encoder Mode for direction, with edge timestamps from TIM5 for RPM.
  TIM3 overflow callback (Encoder_TIM3_OvfCallback) handles stopped detection.

  Functions:
    Encoder_Init()              — Reset state, start TIM2/TIM3 encoders
    Encoder_GetRPM_Left()       — Return latest left wheel RPM (signed)
    Encoder_GetRPM_Right()      — Return latest right wheel RPM (signed)
    Encoder_TIM3_OvfCallback()  — Called from TIM3 IRQ to detect motor stop

--- 3.4  ibus.c / ibus.h  (Core/Src/ibus.c, Core/Inc/ibus.h) ---

  Replaces BBB flysky_receiver.py + pyserial.

  Protocol: 32-byte iBUS frames at 115200 baud.
  Header: [0x20, 0x40]. 10 channels × 2 bytes (little-endian). 2-byte checksum.
  Checksum: 0xFFFF − sum of first 30 bytes.

  Implementation uses DMA + UART IDLE interrupt:
    - HAL_UART_Receive_DMA() fills dma_buf[32] in background
    - UART IDLE interrupt fires when frame gap detected
    - IBUS_IdleCallback() stops DMA, parses frame, restarts DMA

  Functions:
    IBUS_Init()               — Enable IDLE IT, start DMA receive
    IBUS_IdleCallback()       — Parse frame on idle line detection
    IBUS_GetChannels()        — Return latest channel array (IRQ-safe copy)
    IBUS_IsSignalOk()         — Returns 1 if frame received within 400 ms
    IBUS_GetXn()              — Normalised steering (-1.0 to +1.0)
    IBUS_GetYn()              — Normalised throttle (-1.0 to +1.0)
    IBUS_GetFwdSpeedLimit()   — SWC mapped to 0.30/0.60/1.00
    IBUS_GetRevSpeedLimit()   — SWB mapped to 0.60/1.00
    IBUS_IsSWD_On()           — SWD arm/disarm toggle (threshold 1450)

--- 3.5  pipeline.c / pipeline.h  (Core/Src/pipeline.c, Core/Inc/pipeline.h) ---

  Replaces BBB pipeline.py.
  Implements differential drive mixer:
    (Xn, Yn) → motion state → (rpm_L, rpm_R, dac_L, dac_R)
  States: FORWARD, REVERSE, SPOT_TURN, BRAKE, STOP
  Applies SWC/SWB speed caps, EPSILON steering curve, MIN_RATIO inner wheel.

--- 3.6  main.c control loop  (Core/Src/main.c) ---

  20 Hz loop driven by TIM4 period interrupt.
  Loop body:
    1. Read IBUS channels
    2. Check SWD → arm/disarm contactor (with debounce)
    3. If armed & signal OK → run pipeline → Motor_SetSpeeds / Motor_Brake
    4. If RC lost → Motor_Brake (failsafe)
    5. Read encoders (for future PID / telemetry)

  Initialisation sequence (USER CODE BEGIN 2):
    Motor_Init()
    Encoder_Init()
    IBUS_Init()
    Motor_Energize()              ← auto-arm on boot
    last_contactor_ts = TIM5->CNT

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  BUG #1 — Contactor Not Clicking on Boot
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Symptom: After first flash, contactor did not click. On BBB, the contactor
           clicked automatically on boot (confirming system ready). On STM32
           the only contactor trigger was the SWD rising-edge detection.

  Root cause: Original STM32 code only energised on SWD toggle (rising edge
              detect). No auto-energise on startup.

  Fix: Added Motor_Energize() call in USER CODE BEGIN 2 of main.c,
       immediately after Motor_Init() / IBUS_Init():

         Motor_Energize();
         last_contactor_ts = TIM5->CNT;  // start debounce from this moment

  Result: Contactor clicks ~500 ms after boot — same behaviour as BBB.
          Confirmed working by user.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  BUG #2 — iBUS Not Receiving (FlySky RC Unresponsive)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Symptom: Contactor clicked (boot confirmed), FlySky bound to receiver,
           but no stick movement / switch commands had any effect.

  --- Sub-bug A: NVIC not enabled for USART1 ---

    Root cause: CubeMX does not automatically add NVIC enable calls in
                HAL_UART_MspInit() unless "NVIC" is explicitly configured
                in the CubeMX NVIC panel. It was not set.
                Result: USART1 interrupts never fired.

    Fix: Manually added to stm32f4xx_hal_msp.c in USER CODE section
         inside HAL_UART_MspInit():

           HAL_NVIC_SetPriority(USART1_IRQn, 5, 0);
           HAL_NVIC_EnableIRQ(USART1_IRQn);

  --- Sub-bug B: DMA not configured — HAL_UART_Receive_DMA() silently failed ---

    Root cause: ibus.c called HAL_UART_Receive_DMA() but DMA2 Stream 2
                was never enabled in CubeMX. The huart1.hdmarx pointer was
                NULL. The call returned HAL_ERROR silently — no assertion,
                no crash — just no data ever arrived in the buffer.

    Fix: User added DMA to CubeMX configuration:
           DMA2, Stream 2, Channel 4, Direction = Peripheral→Memory,
           Mode = Normal, Data Width = Byte/Byte.
         CubeMX regenerated MX_DMA_Init() and added it BEFORE MX_I2C1_Init()
         in main.c (correct order — DMA must init before peripherals that use it).

  --- Sub-bug C: Duplicate USART1_IRQHandler after CubeMX regeneration ---

    Root cause: After CubeMX regenerated stm32f4xx_it.c, it added its own
                USART1_IRQHandler(). Our previous USER CODE still had a
                duplicate handler inside USER CODE BEGIN 1. Two handlers
                for same IRQ = linker error / undefined behaviour.

    Fix: Removed our duplicate handler from USER CODE BEGIN 1.
         Moved IDLE detection into the CubeMX-generated handler using
         USER CODE sections:

           /* In USART1_IRQHandler, USER CODE BEGIN USART1_IRQn 0: */
           if (__HAL_UART_GET_FLAG(&huart1, UART_FLAG_IDLE))
               IBUS_IdleCallback();

  --- Sub-bug D: IDLE flag clearing (STM32F4 specific) ---

    On STM32F4, IDLE flag is cleared by reading SR then DR (not by a
    simple macro). The correct macro is __HAL_UART_CLEAR_IDLEFLAG()
    which performs the SR→DR read sequence.
    Confirmed this was used correctly in IBUS_IdleCallback().

  --- Physical Connection Note ---

    iBUS receiver signal line runs at 5 V logic level.
    BBB was protected by a voltage divider (5V → 3.3V) on the PCB.
    STM32 PA10 is 5V-tolerant on STM32F4, so the same PCB voltage divider
    is compatible. User confirmed physical connection using jumper wires
    from PCB's P9_19 and P9_20 pads to STM32 PB6 and PB7.

  Result: After all four sub-bugs fixed, iBUS reception working.
          SWD arm/disarm confirmed working (contactor clicks).

  BUG #3 — Motor Throttle Not Responding (Stick Movement No Effect)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Symptom: iBUS working (SWD contactor toggle confirmed), but moving throttle
           / steering sticks caused no voltage change on DAC output pins.

           I2C SDA (PB7) and SCL (PB6): both read 3.2 V (pull-ups working).

  --- Sub-bug A: Missing MCP4725 command byte ---

    Root cause: Original _WriteDac() sent only 2 bytes (upper nibble, lower
                nibble). The MCP4725 requires a 3-byte transaction:
                  Byte 0: 0x40 (Write DAC Register, no EEPROM)
                  Byte 1: D[11:4]
                  Byte 2: D[3:0] << 4
                Without the command byte, the chip interpreted the data bytes
                as a command (0x00 = fast write to DAC+EEPROM with value 0),
                so it output 0 V consistently regardless of what we sent.

    Reference: BBB used Python smbus2:
                 write_i2c_block_data(addr, 0x40, [upper, lower])
               Which sends exactly 3 bytes: command=0x40, then 2 data bytes.

    Fix: Rewrote _WriteDac() in motor.c:

           static void _WriteDac(uint8_t addr, uint16_t value)
           {
               if (value > DAC_MAX) value = DAC_MAX;
               uint8_t buf[3];
               buf[0] = 0x40U;
               buf[1] = (uint8_t)((value >> 4) & 0xFFU);
               buf[2] = (uint8_t)((value << 4) & 0xFFU);
               HAL_I2C_Master_Transmit(&hi2c1, (uint16_t)(addr << 1),
                                       buf, 3U, 50U);
           }

  --- Sub-bug B: I2C speed incompatible with 4.7 kΩ pull-up resistors ---

    Root cause: I2C1 was configured at 400 kHz (Fast Mode).
                Fast Mode requires signal rise time ≤ 300 ns.
                PCB pull-up resistors: 4.7 kΩ to 3.3 V.
                Bus capacitance: ~100 pF (typical PCB trace + chip input).
                Rise time = 0.8473 × R × C ≈ 0.8473 × 4700 × 100e-12 ≈ 398 ns
                            (or simple RC: τ = 470 ns → 63% in 470 ns)
                This exceeds the 300 ns limit → I2C framing errors → no ACK.

    Fix: Changed I2C1 clock from 400 kHz to 100 kHz (Standard Mode).
         At 100 kHz, rise time limit is 1000 ns — well within 470 ns actual.
         Changed in main.c MX_I2C1_Init():

           hi2c1.Init.ClockSpeed = 100000;

         Also increased _WriteDac() HAL timeout from 10 ms to 50 ms.

    IMPORTANT NOTE: If CubeMX is ever used to regenerate code, the I2C1
                    must be set to "Standard Mode 100 kHz" in CubeMX,
                    otherwise regeneration will overwrite this back to 400 kHz.

  Status: Fix applied (100 kHz I2C + correct 3-byte DAC command).
          Rebuild and flash pending at end of Session 2.
          Expected result: multimeter on DAC Vout should now show voltage
          changing (0 V → ~3.3 V range) as throttle stick is moved.

  BUG #4 — Reverse Does Nothing (Stays Forward); Left Steering Does Nothing
  (Stays Right) — Found and Fixed 2026-07-30
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Symptom: Forward throttle and right steering worked correctly. Reverse
           throttle had no effect (motors kept driving forward). Left
           steering had no effect (rover kept turning right regardless of
           stick position).

  Root cause: Core/Src/ibus.c, _ToFloat(). IBUS_VAL_MIN/MID/MAX are #define'd
              in config.h with a U suffix (unsigned int). The line

                norm = (float)(raw - IBUS_VAL_MID) / ...

              forces `raw - IBUS_VAL_MID` into UNSIGNED arithmetic whenever
              raw < IBUS_VAL_MID (i.e. any stick position below center —
              reverse throttle or left steering). Example: raw=1000,
              IBUS_VAL_MID=1500 → 1000u - 1500u does not give -500, it wraps
              to 4294966796u. Cast to float, that's ~+8.59 million instead
              of -1.0.

              Downstream, this huge positive garbage value:
                - As Yn: going_fwd = (Yn > 0.0f) evaluates true regardless
                  of intent → robot always computed as driving forward.
                - As Xn: the steering formula treats it as a large positive
                  (right-side) command → robot always steered as if turning
                  right.

              Values with raw >= IBUS_VAL_MID (forward throttle, right
              steering) never hit the wraparound, which is why those
              directions worked and the negative side silently didn't.

              This bug has no equivalent in the original BBB Python
              (drivers/flysky_receiver.py `_to_float`) — Python integers
              are arbitrary-precision and signed, so `raw - IBUS_MID` just
              works. It was introduced purely by the C port picking up the
              `U` suffix on the config constants.

  Fix: Cast to a signed type before subtracting, in Core/Src/ibus.c:

         int32_t diff = (int32_t)raw - (int32_t)IBUS_VAL_MID;
         norm = (float)diff / (float)(IBUS_VAL_MID - IBUS_VAL_MIN);   /* or MAX-MID */

       Scanned the rest of Core/Src for the same "(unsigned constant) -
       (unsigned constant)" pattern — no other occurrence found.

  Status: Fixed in source. Rebuilt and flashed 2026-07-30 along with Bug #5
          below (both found in the same test session).

              from Encoder_Init() — does NOT enable TIM3's Update interrupt.
              Checked the HAL source directly
              (Drivers/STM32F4xx_HAL_Driver/Src/stm32f4xx_hal_tim.c,
              HAL_TIM_Encoder_Start_IT, TIM_CHANNEL_ALL branch): it enables
              TIM_IT_CC1 and TIM_IT_CC2 — the capture-compare interrupts
              that fire on every quadrature edge — not TIM_IT_UPDATE.

              TIM3_IRQHandler (added earlier this session) only checked and
              cleared the UPDATE flag:

                if (__HAL_TIM_GET_FLAG(&htim3, TIM_FLAG_UPDATE) && ...)
                    __HAL_TIM_CLEAR_IT(&htim3, TIM_IT_UPDATE);

              So the first time the right wheel turned and generated a
              CC1/CC2 edge: TIM3_IRQn fired (now unmasked at NVIC by this
              session's earlier fix) → the ISR's UPDATE check was false →
              the CC1/CC2 flag that caused entry was never cleared → the
              IRQ re-fired the instant the ISR returned → infinite interrupt
              storm → main loop starved of CPU forever. The contactor had
              already clicked (in Motor_Energize(), called before the first
              wheel ever turns), so it looked "engaged" while everything
              else silently died the moment the wheels first moved.

              CC1/CC2 flags set harmlessly and nothing ever serviced them —
              which is also why the original 16-bit-overflow problem (the
              thing the NVIC fix was trying to solve) never caused a crash,
              just silently-wrong RPM after ~82s of continuous rotation.

       overflow tracking to polling, since Encoder_Update() already runs
       every 20 Hz tick and a 16-bit counter at max wheel speed doesn't
       wrap for ~82s (huge margin vs. a 50ms poll interval):
         - encoder.c: Encoder_Init() now calls HAL_TIM_Encoder_Start()
           (non-IT) for TIM3, same as TIM2.
         - encoder.c: Encoder_Update() now polls and clears
           __HAL_TIM_GET_FLAG(&htim3, TIM_FLAG_UPDATE) once per call and
           invokes the (now-static, internal) overflow handler directly —
           no ISR involved.
         - stm32f4xx_it.c: removed the TIM3_IRQHandler USER CODE block
           entirely (left a comment explaining why, to stop this from being
           reintroduced the same way). TIM3's vector now falls through to
           the default weak handler, which is correct since NVIC is masked.
         - stm32f4xx_hal_msp.c: removed the TIM3_IRQn NVIC enable from
           HAL_TIM_Encoder_MspInit() (left a comment pointing at the polling
           approach instead).
         - encoder.h: removed Encoder_TIM3_OvfCallback() from the public
           API — it's internal-only now (renamed _TIM3_OvfHandler, static).

  Lesson: HAL_TIM_Encoder_Start_IT() enables CC1/CC2 (edge) interrupts, NOT
          the Update interrupt, regardless of channel argument. If you need
          Update/overflow interrupts alongside encoder mode, either handle
          CC1/CC2 in the ISR too (e.g. by calling HAL_TIM_IRQHandler(), which
          services all three), or don't use interrupts for the overflow
          case at all — poll it from wherever you already read the counter
          on a fixed schedule, as done here.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

           audibly and SWD-triggered arm/disarm via the transmitter works
           (both confirmed) — but no forward/reverse/any movement happens.
           Pressing the STM32's own RESET button (not a full power cycle)
           immediately fixes it; everything then works normally for the
           rest of that session.

  Hypothesis: contactor (GPIO) and iBUS/SWD (UART) both work fine on cold
              boot, and both are entirely independent of I2C — the only
              thing broken is anything that depends on writing the DAC
              over I2C. That narrows this specifically to I2C, not a
              general MCU boot problem.

              The STM32 itself boots and starts executing within low
              single-digit milliseconds of power being applied. The rest
              of the board (DAC supply rail, whatever regulator feeds the
              MCP4725s) likely has a slower power-up ramp. Motor_Init()
              runs almost immediately after boot and previously attempted
              its first _WriteDac() calls before that supply had
              necessarily stabilised. An I2C transaction attempted against
              a not-yet-powered (or only-just-powering) slave can leave
              the bus or the STM32's own I2C1 peripheral state wedged, so
              every LATER I2C transaction keeps failing too — even once
              the DAC is fully powered — because the bus/peripheral state
              is stuck, not because the DAC isn't ready anymore.

              A manual reset re-runs the exact same init sequence, but by
              the time a human presses the button, the DAC rail has long
              since stabilised (seconds have passed since cold power-on),
              so the same sequence that failed at cold boot succeeds
              cleanly on reset. This matches the reported behaviour
              exactly (reset fixes it, power-up alone doesn't).

  Fix (single isolated change, per the one-change-at-a-time rule):
       Core/Src/motor.c — added _WaitForDacsReady(), called at the very
       start of Motor_Init(), BEFORE the first _WriteDac() calls. Polls
       HAL_I2C_IsDeviceReady() for both DAC_LEFT_ADDR and DAC_RIGHT_ADDR
       every 50ms, capped at a hard 2s timeout (falls through and
       proceeds anyway if the DAC genuinely never responds — no worse
       than current behaviour in a true hardware-fault case). Confirmed
       HAL_I2C_IsDeviceReady() itself is internally bounded (uses
       I2C_WaitOnFlagUntilTimeout for the BUSY flag, returns HAL_BUSY
       rather than hanging) — verified directly in
       Drivers/STM32F4xx_HAL_Driver/Src/stm32f4xx_hal_i2c.c.

       Note: TIM5 is not started until Encoder_Init(), which runs AFTER
       Motor_Init() in main.c. Since _WaitForDacsReady() needs TIM5 for
       its own polling delay, it calls HAL_TIM_Base_Start(&htim5) itself
       first — Encoder_Init() starting it again afterward is harmless
       (idempotent).

  Caveat / what this does NOT rule out: HAL_I2C_IsDeviceReady() itself
  issues a real I2C START condition and address probe — it's not a passive
  check. If the actual failure mode is the DAC ACTIVELY holding SDA low
  while partially (not fully) powered — rather than simply being absent/
  unpowered and giving a clean no-ACK — then the very first readiness
  probe could wedge the bus the same way a raw write would, and this fix
  wouldn't help. This is considered less likely (a fully unpowered device
  typically gives a clean timeout, not a wedge — wedging usually needs an
  actively-driving device that gets interrupted mid-transaction), but
  isn't proven either way without hardware access. If this fix does NOT
  resolve the symptom, the next thing to try is an active I2C bus-recovery
  routine (manually clock SCL as GPIO for up to 9 pulses to unstick a
  slave before HAL_I2C_Init() runs) — not implemented, only try this if
  the current fix fails, and still one change at a time.

  FIX — Forced Software Self-Reset on Cold Boot (opened same session as
  above, not yet tested)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Since waiting-and-probing didn't resolve the cold-boot I2C issue, and a
  manual reset reliably does, the user asked to automate exactly that:
  wait a few seconds after power-up, then force a reset in software so the
  full init sequence re-runs once the DAC rail has had time to settle —
  same effect as pressing the physical reset button, done automatically.

  Danger avoided: a naive "always wait N seconds then reset" would reset
  in an infinite loop, since triggering NVIC_SystemReset() itself causes
  another boot that would see the same "wait then reset" code and repeat
  forever. Fixed by checking RCC->CSR's reset-cause flags, which persist
  across a reset until explicitly cleared:
    - RCC_FLAG_PORRST / RCC_FLAG_BORRST → genuine power-on/brown-out reset
      (a real cold boot) → run the wait-then-reset logic.
    - RCC_FLAG_SFTRST → the reset was caused by our own NVIC_SystemReset()
      call → skip the block entirely, proceed straight to normal init.
    - RCC_FLAG_PINRST (manual reset button) → also skipped, so a user
      pressing reset later in a session doesn't re-trigger this.

  Implementation — Core/Src/main.c, in the USER CODE Init section, right
  after HAL_Init() and BEFORE SystemClock_Config() or any peripheral init
  (so nothing touches I2C/GPIO/etc. during the wait):

    if (__HAL_RCC_GET_FLAG(RCC_FLAG_PORRST) || __HAL_RCC_GET_FLAG(RCC_FLAG_BORRST))
    {
        __HAL_RCC_CLEAR_RESET_FLAGS();
        HAL_Delay(3000);
        NVIC_SystemReset();   /* never returns */
    }
    __HAL_RCC_CLEAR_RESET_FLAGS();

  HAL_Delay() works correctly here even though this runs before
  SystemClock_Config() — HAL_Init() already configured SysTick against
  whatever clock is active at that point (default post-reset HSI), and
  SystemClock_Config()'s HAL_RCC_ClockConfig() call re-calibrates SysTick
  for the new 100MHz clock afterward on the "real" boot — the two don't
  conflict since they happen in separate boot cycles.

  Known behavioural change: every cold power-up now takes ~3s longer
  before the contactor click ("system ready" indicator) is heard — click
  now happens at roughly T+3s+(normal boot time)+500ms settle, not
  immediately. This is expected; the delay is the whole point. During the
  3s wait itself nothing is armed and no peripherals besides the default
  clock are touched, so there's no new safety exposure in that window —
  the DAC path wasn't working during an equivalent window before this fix
  either.

  3000ms is the user's empirically-confirmed manual-reset wait; may need
  tuning (shorter/longer) based on further cold-boot testing.

  Root cause (confirmed via web search, not just internal reasoning this
  time): a reset — hardware NRST OR software NVIC_SystemReset() — ONLY
  clears the STM32's own internal peripheral/register state. It has NO
  effect on an external I2C slave that is actively holding SDA (or SCL)
  low. If the MCP4725 DAC was mid-transaction when its supply was still
  ramping up during cold boot, it can freeze holding SDA low, waiting for
  clock pulses that never arrive. When I2C1 re-initialises after ANY kind
  of reset, it immediately sees SDA held low and reports BUSY again —
  identical symptom to what we saw. This is a well-documented, independently
  confirmed STM32 I2C failure mode:
    - ST Community: "Can't reset I2C in STM32F407 to release I2C lines"
      https://community.st.com/t5/stm32-mcus-products/can-t-reset-i2c-in-stm32f407-to-release-i2c-lines/td-p/463531
      — user found HAL_I2C_DeInit()/re-init and even the SWRST bit did NOT
      release the lines; the fix that worked was: reconfigure SCL/SDA as
      GPIO outputs, generate 9 manual clock pulses, THEN reset/reinit I2C.
    - "Resolving STM32F4xx I2C Stuck Busy After MCU Software Reset"
      https://www.zyma.me/post/stm32f4-i2c-busy-after-software-reset/
      — STM32F4-specific, same symptom (stuck BUSY surviving a software
      reset), same fix: bit-bang ~10 SCL pulses with SDA held high (NACK),
      then leave SCL high (idle) before re-initialising I2C as a peripheral.
    - General I2C-bus spec background: the BUSY flag reflects live GPIO
      bus state, not just internal register state, so an internal reset
      can't clear it while an external device is still physically driving
      a line low.

    - Added _I2C1_BusRecovery() (USER CODE 0, before main()): configures
      PB6/PB7 as plain open-drain GPIO (not I2C yet), releases SDA (lets
      the 4.7k pull-up bring it high), clocks SCL 9 times, then generates

      bus cleanly idle. Pure GPIO bit-banging — the I2C1 peripheral isn't
      touched at all here.

  Context: four consecutive fix attempts all failed (DAC-ready polling,
  forced software self-reset, boot-time bus recovery, delay + recovery
  combined). All four shared one assumption: that the fault was purely an
  I2C bus/timing problem. The key evidence that DISPROVES that assumption
  had been overlooked — the 3s-delay-then-reset attempt produced a
  correctly-delayed contactor click (so the delay definitely ran, and the
  DAC rail had a full 3 seconds to stabilise) and STILL no movement. If
  this were only "DAC not powered up in time," that attempt should have
  worked. It didn't. So the I2C-timing story is at best incomplete.

  New root-cause hypothesis (fits EVERY observation, including the ones
  the previous theories could not explain):

    The BLDC controllers latch a refuse-to-run fault at the moment the
    contactor closes, and only a contactor power-cycle clears it.

    E-scooter BLDC controllers near-universally self-check "is throttle at
    zero?" at their own power-up, latching a fault if it isn't (standard
    anti-runaway safety). The contactor is what feeds them power — so the
    instant the contactor closes IS their power-up moment.

    - COLD BOOT: the MCP4725 powers up outputting whatever is in its
      internal EEPROM, which is not necessarily 0 V. Motor_Init() attempts
      to write 0, but if that write fails (bus not yet healthy), the DAC
      is STILL sitting at that non-zero voltage when Motor_Energize()
      closes the contactor ~immediately after. Controllers power up, see
      non-zero throttle, latch fault. From that moment no amount of
      correct DAC writes will move the wheels — the controllers are done
      until power-cycled.

    - AFTER PRESSING RESET: the DAC is NOT power-cycled by an STM32 reset
      — it stays powered and keeps holding the 0 V written during the
      previous session. Motor_Init() opens the contactor, Motor_Energize()
      re-closes it, and the controllers power up seeing a clean, genuine
      0 V → no fault latched → everything works. THIS is why the reset
      button "fixes" it, and why it looked like an MCU-side problem when
      it never was.

  This also explains why the immediately-preceding fix failed: that
  revision called _I2C1_Recover() from Motor_Energize() but placed it
  AFTER the contactor GPIO was already set high and after the 500 ms
  settle. The controllers had already latched their fault half a second
  before the recovery code ever executed. Right idea, fatally wrong place.

  Fix — Core/Src/motor.c:
    - _WriteDacChecked(): new variant of _WriteDac() that RETURNS the HAL
      status instead of discarding it (the long-standing gap first noted
      back in the "Open Investigation" entry, finally acted on).
      _WriteDac() is kept as a fire-and-forget wrapper for the normal
      driving path, where a single failed mid-manoeuvre write isn't
      independently actionable.
    - _EnsureDacsZeroed(): writes 0 to BOTH DACs and verifies both
      transactions actually returned HAL_OK. On failure it runs
      _I2C1_Recover() and retries, up to 5 attempts. On success it waits
      50 ms for 0 V to settle at the controller input before returning.
    - Motor_Energize(): now calls _EnsureDacsZeroed() FIRST, and only
      closes the contactor if it returns success. The post-close
      _I2C1_Recover() call from the previous revision is removed (it was
      unreachable-by-design as a fix — see above).
    - If zero throttle CANNOT be confirmed: the contactor is deliberately
      NOT closed, and PC13 (onboard LED, active-LOW, confirmed unused) is
      latched on. Rationale: closing the contactor with an unknown
      throttle voltage risks both the fault latch AND a genuine unexpected
      lurch. The rover would not have driven in that state anyway, so
      refusing costs no capability while removing a real hazard.
    - _DiagLedInit() called from Motor_Init().

    Each outcome eliminates a different half of the remaining problem
    space, so this build produces useful information even if it doesn't
    fix the symptom.

  ── THE SYMPTOM ─────────────────────────────────────────────────────────

  After a cold power-up, the contactor clicked and the FlySky RC worked
  (arm/disarm responded), but the wheels would not move in any direction.
  Pressing the STM32's physical RESET button made everything work
  perfectly for the rest of that session. Power cycle → broken again.

  ── THE ACTUAL CAUSE ────────────────────────────────────────────────────

  The firmware was trying to talk to the MCP4725 DACs at a point in the
  boot sequence when the DACs were not yet able to respond, and those
  failed transactions left the I2C bus in a wedged state that never
  recovered on its own — so every later DAC write failed too, and the
  throttle output stayed at 0 V forever.

  Sequence on a COLD BOOT (broken):
    1. STM32 powers up and starts executing within milliseconds.
    2. Motor_Init() immediately fires I2C writes at the DACs to zero the
       throttle — while the DACs are not yet able to answer.
    3. Those writes fail. Critically, a failed transaction against a
       not-yet-ready I2C slave can leave SDA held low / the I2C1
       peripheral latched in an error state. The bus is now WEDGED.
    4. The contactor closes. Everything downstream is now powered.
    5. But the bus is still wedged from step 3 — so every DAC write from
       the main control loop also fails. DAC output never changes.
       Throttle stays at 0 V → no movement, forever.

  Sequence after pressing RESET (worked, and this is the clue that cracked
  it):
    1. The DACs were ALREADY powered and settled from the previous
       session — an STM32 reset does not power-cycle them.
    2. Motor_Init()'s I2C writes therefore SUCCEED on the first try.
    3. The bus never wedges. Every subsequent write works. Full movement.

  That is the whole puzzle: reset "fixed" it not because it reset the
  STM32, but because by the time a human pressed the button, the DAC side
  had long since become ready — so the early writes that normally wedge
  the bus succeeded instead.

  ── WHY EARLIER FIX ATTEMPTS ALL FAILED ─────────────────────────────────

  Five attempts failed because every one of them tried to fix things
  BEFORE or AT the point the contactor closes, and none of them ever
  VERIFIED that a DAC write actually landed afterwards:

    1. _WaitForDacsReady() polling HAL_I2C_IsDeviceReady() in Motor_Init()
       — the readiness probe is itself a real I2C transaction, so it could
       wedge the bus exactly like the write it was trying to protect.
    2. 3s delay + NVIC_SystemReset() on cold boot — a reset only clears
       the STM32's own state; it cannot make an external slave release a
       held-low line, and cannot un-wedge the bus.
    3. _I2C1_BusRecovery() bit-banging at boot — ran before the DAC side
       was ready, so it cleared a bus that then simply got re-wedged.
    4. 3s delay THEN bus recovery — same problem, just later.
    5. Gating the contactor on DAC success — caused a hard deadlock (see
       DEADLOCK entry above) and had to be reverted immediately.

  ── WHAT ACTUALLY FIXED IT ──────────────────────────────────────────────

  Core/Src/motor.c, Motor_Energize(). The working ingredient is doing the
  DAC zeroing AFTER the contactor has closed and settled, and — the part
  that matters most — VERIFYING the write actually returned HAL_OK, with
  I2C bus recovery and retry if it did not:

      void Motor_Energize(void)
      {
          if (is_energized) return;

          /* best effort, must NOT block arming */
          if (!_EnsureDacsZeroed()) _DiagLedOn();

          HAL_GPIO_WritePin(Contactor_GPIO_Port, Contactor_Pin, GPIO_PIN_SET);
          _DelayUs(500000U);          /* 500 ms contactor settle */
          is_energized = 1;
          armed        = 1;

          /* THE FIX: retry AFTER the contactor is closed and settled.
           * This is the first moment the DAC side is reliably able to
           * respond — and unlike every earlier attempt, this one CHECKS
           * that the write landed and runs bus recovery + retries if not. */
          if (_EnsureDacsZeroed()) _DiagLedOff();
      }

  The two supporting pieces that make that line work:

    · _WriteDacChecked() — returns the HAL status instead of discarding
      it. The original _WriteDac() threw the return value away, which is
      precisely why a wedged bus could go undetected indefinitely. This
      gap existed from the very first version of motor.c and was the
      single biggest obstacle to diagnosing this — the firmware had no
      idea its writes were failing.

    · _EnsureDacsZeroed() — writes 0 to both DACs, checks BOTH statuses,
      and on failure runs _I2C1_Recover() (de-init I2C1, bit-bang 9 SCL
      pulses to force any stuck slave to release the bus, manual STOP,
      re-init I2C1) then retries. This is what un-wedges a bus that got
      stuck during the early boot writes.

  In short: the earlier bus-recovery code was RIGHT, but it was being run
  at the wrong time and its result was never checked. Moving it after the
  contactor closes and verifying the outcome is what closed the issue.

    needs exactly 48 MHz from PLLQ, and the current clock tree gives 50 MHz

                 → PLLP 2 → 100 MHz SYSCLK ✓
                 → PLLQ 4 →  50 MHz USB    ✗ (needs 48)
    On STM32F411 the USB clock can ONLY come from PLLQ (no PLLSAI/CK48M mux
    like the larger F4 parts), so there is no way to have both 100 MHz
    SYSCLK and valid USB. The only valid combination is a 192 MHz VCO →
    96 MHz SYSCLK + 48 MHz USB. That would have dropped HCLK 100 → 96 MHz,
    which silently breaks the TIM5 microsecond timebase (prescaler 99 gives
    0.96 MHz instead of 1 MHz — every delay, the RC timeout, the loop
    period, the contactor debounce and the DAC ramp all 4 % off) and would
    have needed TIM5 prescaler 99 → 95 in the same step, plus USB_DEVICE
    CDC middleware and a large regeneration. Judged far too much
    interconnected change at once for the benefit.

  ROUTE 3 — UART → ESP32 → USB serial monitor  ✅ ADOPTED AND WORKING
    STM32 PA9 (USART1_TX) → ESP32 DevKit V1 GPIO16 (RX2), plus common GND.
    ESP32 runs a pass-through sketch bridging its UART2 to USB, read in the
    Arduino IDE Serial Monitor at 115200.
    Chosen because it needed ZERO CubeMX changes (PA9 was already
    configured as USART1_TX with UART_MODE_TX_RX), no clock change, no
    debugger, and works with the CubeProgrammer flash workflow that was
    already functioning. It also aligns with an existing roadmap item —
    Section 7 already called for "telemetry → UART to ESP32/ESP8266".

  ── CRITICAL WIRING RULE ────────────────────────────────────────────────

  ONE DIRECTION ONLY: STM32 PA9 → ESP32 GPIO16, plus GND.
  NOTHING may be connected to STM32 PA10. PA10 is USART1_RX and carries the
  FlySky iBUS signal; driving it from the ESP32 would collide with the RC
  link and break control while motors are armed.
  Both devices are 3.3 V logic, so PA9 connects directly — no level shifter.

  ── CODE ADDED ──────────────────────────────────────────────────────────

  Core/Inc/encoder.h + Core/Src/encoder.c
    · Encoder_GetCount_L() / Encoder_GetCount_R() — expose the raw extended
      counter values (return prev_count_l / prev_count_r, the values
      Encoder_Update() last sampled). Deliberately printed ALONGSIDE RPM:
      raw counts prove the hardware and wiring work, RPM proves the maths
      works. Counts moving with RPM wrong = firmware bug; counts frozen =
      wiring/pin problem. Separating those saves a debugging cycle.

  Core/Src/main.c
    · _DbgPutc() — writes USART1->DR DIRECTLY, deliberately NOT via
      HAL_UART_Transmit(). REASON: HAL_UART_Transmit() takes
      __HAL_LOCK(huart1) and holds it for the entire blocking send; if the
      iBUS IDLE interrupt fires in that window, the HAL_UART_Receive_DMA()
      inside IBUS_IdleCallback() returns HAL_BUSY, the RX DMA is never
      restarted and RC frames are dropped. With iBUS frames every ~7 ms and
      a multi-ms send, collisions would be frequent — unacceptable with
      motors powered. TX and RX are independent paths inside the USART, so
      a direct DR write cannot disturb the RX DMA and never touches the
      HAL lock.
      The TXE busy-wait is hardware-bounded (~87 us/char at 115200) since
      the transmitter always drains whether or not anything is listening —
      so it can never stall the 20 Hz loop, and it is safe even with
      nothing connected to PA9.
    · _DbgPuts() — string wrapper.
    · _FmtRpm() — formats a float RPM as e.g. "+12.50" WITHOUT using %f.
      newlib-nano omits float formatting unless -u _printf_float is added
      to the linker flags, and silently prints nothing or garbage
      otherwise. Formats via scaled integers instead to sidestep it.
    · Debug print block in the main loop, rate-limited to ~4 Hz (every 5th
      tick of the 20 Hz loop). At full 20 Hz a ~70-char line would cost
      ~10 % of every loop cycle; at 4 Hz it is ~2 % and far more readable.

  esp32_bridge/esp32_bridge.ino  (new file, outside the STM32 project)
    ESP32 DevKit V1 pass-through bridge: Serial2 (GPIO16) → Serial (USB).
    Includes a watchdog message if no data arrives for 3 s, which
    distinguishes "bridge broken" from "STM32 not transmitting" — those
    otherwise look identical (a blank screen) and waste debugging time.
    NOTE: GPIO16/17 are free on WROOM-32 (DevKit V1). On WROVER modules
    those pins are used for PSRAM — use GPIO25/26 there instead.

  ── OUTPUT FORMAT ───────────────────────────────────────────────────────

      CMD L+6.00 R+6.00 | ENC L+5.92 R+6.05 | cnt 412 419

      CMD = commanded wheel RPM from the pipeline
      ENC = measured wheel RPM from the encoders
      cnt = raw quadrature counter values (left, right)

    Printing commanded and measured side by side answers several questions
    in one line: is the encoder wired, is its direction correct, and does
    the RPM maths agree with what was asked for. It is also exactly the
    signal needed later for PID tuning.

    Interpreting it:
      · CMD and ENC same sign, magnitudes close   → working correctly
      · ENC sign OPPOSITE to CMD on one wheel     → that encoder's A/B
                                                    phases are swapped
      · One side stuck at +0.00, cnt frozen       → that encoder not wired
      · cnt moves but ENC stays 0.00              → turning too slowly;
                                                    ENC_STOPPED_US (500 ms)
                                                    is zeroing the reading

SECTION 8 — KEY TECHNICAL LESSONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  1. CubeMX does NOT add NVIC enable for UARTs unless the NVIC panel is
     explicitly configured. Always check HAL_UART_MspInit() for missing
     HAL_NVIC_EnableIRQ() calls when interrupts are not firing.

  2. DMA must be enabled in CubeMX before calling HAL_UART_Receive_DMA().
     If hdmarx is NULL, the call returns HAL_ERROR silently — no crash,
     no assertion, just no data. Always verify DMA is in MX_DMA_Init().

  3. MX_DMA_Init() must be called BEFORE any peripheral init (MX_I2C1_Init,
     MX_USART1_UART_Init) in main.c. CubeMX handles this automatically
     when DMA is added via the GUI.

  4. After CubeMX code regeneration, check stm32f4xx_it.c for duplicate
     IRQ handlers. CubeMX will add its own handler for any configured IRQ,
     and any existing USER CODE handler for the same IRQ must be removed.

  5. STM32F4 IDLE flag is cleared by reading SR then DR. The HAL macro
     __HAL_UART_CLEAR_IDLEFLAG() performs this correctly. Never write
     to the flag register directly.

  6. MCP4725 Write DAC Register (0x40) requires 3 bytes total:
       [command=0x40] [D11:D4] [D3:D0 << 4]
     Python smbus2 write_i2c_block_data(addr, 0x40, [hi, lo]) matches this.
     Sending only 2 bytes (missing command byte) causes 0x00 fast-write,
     which always outputs 0 V.

  7. I2C pull-up resistor vs speed: 4.7 kΩ pull-ups → rise time ~470 ns.
     This is within Standard Mode (100 kHz) limit of 1000 ns,
     but exceeds Fast Mode (400 kHz) limit of 300 ns.
     Rule: for 4.7 kΩ pull-ups, always use Standard Mode 100 kHz.
     For Fast Mode 400 kHz: use 2.2 kΩ or 1 kΩ pull-ups.

  8. Auto-energize on boot: clicking the contactor at startup serves as a
     hardware "system ready" indicator — audible confirmation that firmware
     has initialised successfully and motor power is armed.

  9. KNOWN CONTROLLER QUIRK (not a firmware bug — confirmed 2026-07-30 by
     user, present on BOTH BeagleBone and STM32): the BLDC/e-scooter motor
     controller will not engage reverse from a dead stop. The operator must
     briefly command forward first, then reverse, for reverse to actually
     take effect — even though the REV-pin-then-delay sequence (brake
     500ms → release → REV pin HIGH → 150ms settle → 20ms → throttle
     written) is correct and already matches the BBB implementation
     exactly. This is a characteristic of the controller itself (almost
     certainly needs to sense actual prior rotation before permitting
     reversed commutation), not something a firmware delay can fix — don't
     waste time re-tuning REVERSE_BRAKE_US or the dir-change settle time
     to try to eliminate this; it's not a timing problem.

     REVISED same day, more precise info from user: on BBB (after later
     changes), simply HOLDING the reverse command steady for 2-3 seconds
     was enough — no manual toggling needed, even for an abrupt full-
     throttle reverse command. On STM32, sustained holding alone was NOT
     enough; only a GRADUAL pull of the stick, or manually toggling
     forward/reverse repeatedly, got reverse to engage. Both STM32
     workarounds have one thing in common: they make the throttle value
     ramp up gradually instead of jumping straight from 0 to the full
     commanded value in one step (which is exactly what Motor_SetSpeeds()
     was doing — a single _WriteDac() call to the final value right after
     the direction-change delay). This points at the controller rejecting
     an ABRUPT full-throttle-in-reverse command specifically, not simply
     needing more elapsed time. See the DAC ramp experiment in Section 9
     for the fix attempt — this lesson entry will be updated once it's
     verified on hardware.
