Great question — this is one of the most important design decisions for the STM32 port. Let me explain all viable methods and why one clearly wins for your rover.

---

## The 3 Methods

### Method 1: Counter Polling (what BBB did)
Read the encoder counter at fixed intervals, compute delta.

```
RPM = (ΔCounts / counts_per_rev) × (60 / dt)
```

- Hardware counts pulses automatically (encoder mode)
- CPU reads counter only at control loop rate (20Hz)
- Resolution limited at low speed

---

### Method 2: Input Capture — Period/Frequency Method (T method)
Measure the **time between pulses** using a capture timer.

```
RPM = 60 / (pulse_period_seconds × counts_per_rev)
```

- Very accurate at low speed
- Falls apart at high speed (capture timer overflows, pulses arrive too fast)
- Each pulse fires an ISR

---

### Method 3: M/T Method (Hybrid — best of both)
Count pulses **AND** measure the exact time window simultaneously.

```
RPM = (M × 60) / (T × counts_per_rev)
```

Where M = pulses counted, T = exact time measured by separate high-res timer.
Accurate at both low and high speeds.

---

## Why Input Capture Alone Is Dangerous for Your Motor

Your encoder is on the **motor shaft** (before gearbox). At max speed:

```
400 RPM × 2400 counts/rev ÷ 60 = 16,000 pulses/sec per encoder
```

If you fire an ISR per pulse, that's **16,000 ISR calls per second per encoder**, or **32,000 total**. At 100MHz clock, that's only ~3,125 CPU cycles between interrupts — the MCU would spend nearly all its time in ISRs, leaving nothing for your control loop, I2C, or UART.

**Input capture is only suitable when motor speed is very low** (a few hundred RPM max on the shaft). For your 400 RPM max motor, it's not the right choice.

---

## Recommended Approach: Encoder Mode + Overflow Interrupt

This is what TIM2/TIM3 encoder mode is literally designed for:

```
Hardware quadrature decoder → counts all 4 edges per pulse cycle automatically
CPU overhead for counting = ZERO (hardware does it all)
CPU reads counter once per 50ms control loop tick
```

For TIM2 (32-bit, Left encoder): **no overflow handling needed** — at 400 RPM max, it would take ~74 hours to overflow.

For TIM3 (16-bit, Right encoder): enable the **Update interrupt only** to track overflows — this fires at most once every **4 seconds** at max speed, negligible cost.

```c
// TIM3 overflow ISR - fires maybe once every 4 seconds at max speed
void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim) {
    if (htim->Instance == TIM3) {
        // Check direction bit to know if counting up or down
        if (TIM3->CR1 & TIM_CR1_DIR) {
            enc_r_overflow--;   // counting down (reverse)
        } else {
            enc_r_overflow++;   // counting up (forward)
        }
    }
}

// Get 32-bit extended count for TIM3
int32_t get_enc_r_count(void) {
    return (enc_r_overflow << 16) | (int32_t)TIM3->CNT;
}
```

Then RPM calculation in your main 20Hz loop:

```c
// Called every 50ms
void update_encoder_rpm(void) {
    int32_t count_l = (int32_t)TIM2->CNT;         // 32-bit, no overflow issue
    int32_t count_r = get_enc_r_count();           // 16-bit + software extension

    int32_t delta_l = count_l - prev_count_l;
    int32_t delta_r = count_r - prev_count_r;

    prev_count_l = count_l;
    prev_count_r = count_r;

    // (delta / counts_per_rev) * (60 / dt)
    enc_rpm_l = (float)delta_l / 2400.0f * 60.0f / 0.05f;
    enc_rpm_r = (float)delta_r / 2400.0f * 60.0f / 0.05f;
}
```

---

At 20Hz sampling (dt = 50ms):

| Motor RPM | Counts in 50ms | RPM resolution |
|---|---|---|
| 400 (max) | 800 counts | ±0.075 RPM |
| 175 (SPOT turn equivalent) | 350 counts | ±0.17 RPM |
| 100 | 200 counts | ±0.30 RPM |
| 20 | 40 counts | ±1.5 RPM |

Since your motor never runs below ~100 RPM (even spot turns), the resolution is more than adequate for your PID closed-loop controller.

---

## Summary

| Method | CPU Load | Low Speed Accuracy | High Speed Accuracy | Verdict |
|---|---|---|---|---|
| Encoder counter polling | Near zero | OK for your use | Excellent | **Use this** |
| Input capture per pulse | Extreme (16kHz ISR) | Very good | Unusable | Too heavy |
| M/T hybrid | Low | Excellent | Excellent | Overkill for this rover |

**Plan:** Keep TIM2/TIM3 in encoder mode as already configured in CubeMX. Enable TIM3's Update interrupt for overflow tracking. Read counters in the main 20Hz loop. This gives you hardware-level accuracy with essentially zero CPU overhead for counting.

When you generate the CubeMX code, in **TIM3 → NVIC Settings**, enable the **TIM3 global interrupt**. TIM2 needs no interrupt since it's 32-bit.

## Revised STM32 Architecture

**Drop Encoder Mode. Use Input Capture + direction GPIO instead.**

```
Left Encoder A  ──→ PA0  (TIM2_CH1 Input Capture, rising edge)
Left Encoder B  ──→ PA1  (GPIO Input — read in ISR for direction)

Right Encoder A ──→ PA6  (TIM3_CH1 Input Capture, rising edge)
Right Encoder B ──→ PA7  (GPIO Input — read in ISR for direction)

TIM5 (32-bit)   ──→ Free-running counter at 1 MHz (timestamps)
```

**How it works:**

```
Encoder A pulse arrives
    │
    ▼
Input Capture ISR fires
    ├── Read TIM5->CNT  (current timestamp)
    ├── period = current_ts - last_ts
    ├── last_ts = current_ts
    ├── Read PA1 / PA7  (B channel state = direction)
    └── RPM = (60 × 1,000,000) / (period × 600)
              with sign from B channel
```

**Stopped motor handling:** If no pulse arrives for >500ms, force RPM = 0.

## RPM Calculation Code (preview for later)

```c
volatile float wheel_rpm_l = 0.0f;
volatile float wheel_rpm_r = 0.0f;
volatile uint32_t last_cap_l = 0;
volatile uint32_t last_cap_r = 0;
volatile uint32_t last_pulse_time_l = 0;
volatile uint32_t last_pulse_time_r = 0;

void HAL_TIM_IC_CaptureCallback(TIM_HandleTypeDef *htim) {
    uint32_t now = TIM5->CNT;

    if (htim->Instance == TIM2) {
        uint32_t period = now - last_cap_l;
        last_cap_l = now;
        last_pulse_time_l = now;
        if (period > 500) {  // ignore glitches <500µs (>120 RPM — impossible on wheel)
            int8_t dir = HAL_GPIO_ReadPin(GPIOA, GPIO_PIN_1) ? 1 : -1;
            wheel_rpm_l = dir * (60.0f * 1000000.0f) / ((float)period * 600.0f);
        }
    }
    else if (htim->Instance == TIM3) {
        uint32_t period = now - last_cap_r;
        last_cap_r = now;
        last_pulse_time_r = now;
        if (period > 500) {
            int8_t dir = HAL_GPIO_ReadPin(GPIOA, GPIO_PIN_7) ? 1 : -1;
            wheel_rpm_r = dir * (60.0f * 1000000.0f) / ((float)period * 600.0f);
        }
    }
}

// Call this in your 20Hz main loop
void check_encoder_timeout(void) {
    uint32_t now = TIM5->CNT;
    if ((now - last_pulse_time_l) > 500000) wheel_rpm_l = 0.0f;  // >500ms = stopped
    if ((now - last_pulse_time_r) > 500000) wheel_rpm_r = 0.0f;
}
```

## TIM5 in CubeMX

**Timers → TIM5**

| Parameter | Value | Reason |
|---|---|---|
| Clock Source | Internal Clock | No external trigger |
| Counter Mode | Up | Count upward |
| Prescaler (PSC) | **99** | 100MHz ÷ 100 = **1MHz** (1 tick = 1µs) |

| auto-reload preload | Enable | Standard |

## Why 1MHz and Not Higher

At 1µs resolution with TIM5:

```
At 20 wheel RPM: 600 counts/sec → one pulse every 1,667µs
Timing error = ±1µs out of 1,667µs = ±0.06% → ±0.012 RPM
```

More than sufficient. Going to 10MHz would give no real benefit at these speeds and makes arithmetic messier.

---

## How TIM5 Integrates With TIM2/TIM3

Since you're using Encoder Mode (counter-based), TIM5 gives you **precise dt** for the RPM formula rather than relying on `HAL_GetTick()` which only has 1ms resolution:

```c
// Every control loop iteration
uint32_t t_now    = TIM5->CNT;
uint32_t dt_us    = t_now - t_prev;      // handles 32-bit rollover automatically
t_prev            = t_now;

int32_t cnt_l     = (int32_t)TIM2->CNT;
int32_t cnt_r     = (int32_t)TIM3->CNT;

int32_t delta_l   = cnt_l - prev_cnt_l;
int32_t delta_r   = cnt_r - prev_cnt_r;

prev_cnt_l = cnt_l;
prev_cnt_r = cnt_r;

float dt_sec = dt_us * 1e-6f;
float rpm_l  = (delta_l / 2400.0f) * (60.0f / dt_sec);
float rpm_r  = (delta_r / 2400.0f) * (60.0f / dt_sec);
```

TIM5 also doubles as your **stopped detection** — if no encoder count changes and `dt_us > 500000` (500ms), RPM = 0.

---

## One Thing to Watch — Encoder Mode Resolution

Since you chose Encoder Mode (counter-based) on a wheel shaft at max 20 RPM, at your 20Hz loop rate:

```
Max counts per 50ms = 20 RPM × 2400 counts/rev ÷ 60 × 0.05s = 40 counts
SPOT turn (8.75 RPM) = ~17 counts per 50ms
```

17–40 counts gives ±1 count quantization error → **±0.75 RPM to ±1.75 RPM**. That may be too coarse for your PID to tune well at low speed.

**Simple fix using TIM5 — sample faster, average over longer window:**

```c
// Sample at 100Hz (every 10ms), but compute RPM over the last 5 samples (50ms)
// Rolling accumulator — no extra CPU cost
delta_accum_l += (cnt_l - prev_cnt_l);
delta_accum_r += (cnt_r - prev_cnt_r);
sample_count++;

if (sample_count >= 5) {             // every 50ms → 20Hz RPM output
    float dt = (t_now - window_start) * 1e-6f;
    rpm_l = (delta_accum_l / 2400.0f) * (60.0f / dt);
    rpm_r = (delta_accum_r / 2400.0f) * (60.0f / dt);
    delta_accum_l = 0;
    delta_accum_r = 0;
    sample_count  = 0;
    window_start  = t_now;
}
```

This keeps PID running at 20Hz while TIM5 ensures the window dt is exact. Alternatively, if resolution is still insufficient after testing, that's when we'd switch to input capture — but try encoder mode first since you've already configured it.

Internal: one 32-byte DMA buffer, one `IBUSData_t` struct updated atomically on each valid frame.

### `encoder.c / encoder.h` — Wheel RPM
**BBB equivalent:** `_update_encoders()` in `main.py`

Owns TIM2 (left, 32-bit), TIM3 (right, 16-bit), and TIM5 (timestamp). Handles TIM3 16-bit overflow in the ISR. The main loop calls `Encoder_Update()` every tick and reads RPM via getter functions.

```
Encoder_Init()       — start TIM2, TIM3, TIM5; enable TIM3 overflow interrupt
Encoder_Update()     — read counter deltas, compute signed RPM for both wheels
Encoder_GetRPM_L()   — returns float (positive = forward, negative = reverse)
Encoder_GetRPM_R()   — same for right
Encoder_OvfCallback()— called from TIM3_IRQHandler, tracks 16-bit overflow
```

RPM formula inside `Encoder_Update()`:
```
dt_us  = TIM5->CNT - last_ts          (microseconds, 32-bit rollover safe)
delta  = current_count - prev_count   (signed, handles direction)
rpm    = (delta / 2400.0f) * (60e6f / dt_us)
```

Stopped detection: if `dt_us > 500000` (500ms) with no delta change → RPM = 0.

---

### `kinematics.c / kinematics.h` — Differential Drive Math
**BBB equivalent:** `utils/kinematics.py`

Pure math, no hardware dependency. Takes `V` (linear m/s) and `W` (angular rad/s), returns left and right wheel RPM. Stateless — only functions, no global variables.

```
Kinematics_ComputeRPM(V, W, *rpm_L, *rpm_R)
    VL = V - (L/2) * W
    VR = V + (L/2) * W
    rpm_L = (VL / (2π × R)) × 60
    rpm_R = (VR / (2π × R)) × 60
    → scale both if peak exceeds WHEEL_RPM_MAX
    → enforce MIN_RATIO (inner wheel minimum)
```

### `motor.c / motor.h` — Motor Controller
**BBB equivalent:** `drivers/motor_controller.py`

Owns all I2C DAC writes and GPIO direction/brake/contactor control. Tracks internal state (armed, was_reversing, last direction per wheel). The only module that touches GPIOB or writes I2C.

```
Motor_Init()                        — all GPIOs LOW, DAC = 0, armed = false
Motor_Energize()                    — Contactor GPIO HIGH, armed = true
Motor_Deenergize()                  — Contactor GPIO LOW, armed = false
Motor_SetSpeeds(rpm_L, rpm_R,
                dac_L, dac_R)       — set REV GPIOs, release BRAKE, write DAC
Motor_Brake()                       — DAC = 0, BRAKE GPIOs HIGH
Motor_Stop()                        — DAC = 0, all GPIOs LOW
Motor_BrakeThenReverse(...)         — brake for REVERSE_BRAKE_DURATION, then SetSpeeds
Motor_IsArmed()                     — returns armed flag
Motor_WasReversing()                — returns was_reversing flag
```

Internal `_WriteDac(addr, value)` handles the MCP4725 I2C protocol:
```c
uint8_t buf[2] = { (value >> 4) & 0xFF, (value << 4) & 0xFF };
HAL_I2C_Master_Transmit(&hi2c1, addr << 1, buf, 2, HAL_MAX_DELAY);
```

### `pipeline.c / pipeline.h` — Motion State Machine
**BBB equivalent:** `pipeline.py`

Takes normalized RC inputs, returns a `MotionResult_t` struct containing the motion state, V, W, RPMs, and DAC values. No hardware access — pure logic. Uses `kinematics.h` for RPM math.

```
Pipeline_Run(Xn, Yn, fwd_pct, rev_pct, rc_ok, *result)
```

Returns one of these states in `result->state`:

```
BRAKE       → both sticks neutral or rc_ok = false
DISARMED    → contactor off (set by caller before Pipeline_Run)
NO_SIGNAL   → rc_ok false (set by caller)
SPOT_LEFT   → Yn=0, Xn<0  → rpm_R = SPOT_RPM, rpm_L = 0
SPOT_RIGHT  → Yn=0, Xn>0  → rpm_L = SPOT_RPM, rpm_R = 0
FWD         → Yn>0, Xn≈0
FWD_LEFT    → Yn>0, Xn<0
FWD_RIGHT   → Yn>0, Xn>0
REV         → Yn<0, Xn≈0
REV_LEFT    → Yn<0, Xn<0
REV_RIGHT   → Yn<0, Xn>0
```

`MotionResult_t` struct:
```c
typedef struct {
    MotionState_t state;
    float         V;
    float         W;
    float         rpm_L;
    float         rpm_R;
    uint16_t      dac_L;
    uint16_t      dac_R;
} MotionResult_t;
```

### `main.c` — 20Hz Control Loop
**BBB equivalent:** `main.py`

Only orchestration — no hardware details, no math. All `USER CODE` sections.

```
USER CODE BEGIN 2 (after peripheral init):
    IBUS_Init()
    Encoder_Init()
    Motor_Init()

USER CODE BEGIN WHILE (20Hz loop):
    t0 = TIM5->CNT

    IBUS_Read(&rc)

    Contactor_Handle(rc.swd_on)       ← edge detect + 500ms debounce, local to main.c

    if (Motor_IsArmed() && rc.rc_ok):
        Pipeline_Run(..., &result)
        Motor_Execute(&result)        ← dispatch to Motor_Brake/Stop/SetSpeeds etc.
    else:
        Motor_Stop()

    Encoder_Update()

    while (TIM5->CNT - t0 < LOOP_PERIOD_US) {}   ← rate limit to 20Hz
```

### `stm32f4xx_it.c` — ISR Dispatch
**BBB equivalent:** signal handlers in `main.py` — except here ISRs are mandatory

Three additions inside `USER CODE` sections:

USART1_IRQHandler   → calls IBUS_IdleCallback()   (iBUS frame ready)
TIM3_IRQHandler     → calls Encoder_OvfCallback()  (16-bit right encoder overflow)
DMA2_StreamX_IRQHandler → called by HAL for iBUS DMA (HAL handles internally)

We write them in this order so each one can be tested independently before the next depends on it:

1. `config.h` — constants first, everything else references it
2. `kinematics.c/.h` — pure math, testable immediately
3. `encoder.c/.h` — verify RPM numbers before motor runs
4. `ibus.c/.h` — verify RC inputs before motion
5. `motor.c/.h` — verify contactor + DAC before full loop
6. `pipeline.c/.h` — motion logic
7. `main.c` — wire everything together

Here is everything you need:

## Receiver Model
The FS-i6X bundles either the **FS-iA6B** (6ch) or **FS-iA10B** (10ch). The iBUS port is a dedicated 3-pin connector (not a servo channel) — usually labeled **i-BUS** on the receiver body.

## Pin Connection

```
FS-iA6B iBUS Port          STM32F411 (Black Pill)
─────────────────          ──────────────────────
Black  (GND)    ────────── GND
Red    (VCC 5V) ────────── 5V  (from USB or external)
White  (Signal) ────────── PA10 (USART1_RX)
```

**PA10 is 5V-tolerant** on STM32F411, so direct connection is safe — no level shifter needed.

PA9 (TX) does NOT need to be connected. iBUS is receive-only from the STM32 side.

**Common GND is critical** — if the STM32 and receiver are powered from different sources, GND must still be shared.

## Enable iBUS on the Transmitter

On the FS-i6X, iBUS is not enabled by default:

1. Power on transmitter → go to **System** menu
2. Navigate to **RX Setup → Output Mode**
3. Change from PPM/PWM to **iBUS**
4. Confirm and save

Without this step, the receiver outputs PWM on servo channels only — the iBUS port stays silent.

## Quick Check Before Rebuilding

With a multimeter on the white Signal wire (relative to GND):
- Transmitter OFF → ~0V
- Transmitter ON, bound, iBUS enabled → signal toggles rapidly (looks like ~2.5V average on DC mode)

If you see toggling voltage on the signal wire, the receiver is outputting iBUS correctly and the STM32 code should pick it up.
