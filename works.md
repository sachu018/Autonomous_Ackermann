# Works Log — Problems & Precise Solutions

A concise summary of engineering problems encountered and their solutions on the STM32 Agricultural Rover platform.

---

| # | Problem | Root Cause | Precise Solution |
|---|---|---|---|
| 1 | Linker failure on `.ARM.extab` | `(READONLY)` keyword in CubeMX linker script incompatible with GCC 10 | Removed `(READONLY)` from all section definitions in `STM32F411CEUX_FLASH.ld`. |
| 2 | Compile error in `steer_pid.c` | `LOOP_HZ` referenced without including `config.h` | Added `#include "config.h"` in `steer_pid.c`. |
| 3 | Kinematic radius error on sharp turns | `sinf(delta)` used instead of `tanf(delta)` in `Ackermann_ComputeRPM` | Changed turning radius formula to $R_{\text{rear}} = \frac{W_b}{\tan(\delta)}$ in `ackermann.c`. |
| 4 | Steering stalls on transient ADC glitch | `out->valid` set to 0 on single missed read, bypassing 5-tick debounce | Held previous angle and kept `valid=1` until `fault_runs >= STEER_FAULT_THRESHOLD` in `ads1115.c`. |
| 5 | Reverse differential ratio compression | Outer wheel clamped independently in `_ToThrottle` at 10 RPM | Scaled both wheel RPMs down proportionally inside `Ackermann_ComputeRPM` for reverse mode. |
| 6 | Derivative kick on rapid stick movement | PID differentiated on error $(target - actual)$ | Switched PID derivative calculation to derivative-on-measurement in `steer_pid.c`. |
| 7 | Actuator PWM capped at 99.9% | Compare register clamped to ARR (999) instead of ARR+1 (1000) | Allowed `CCR` to reach `ACT_PWM_ARR + 1` at 100% duty cycle in `actuator.c`. |
| 8 | Reverse max speed decoupled from RPM cap | Hardcoded float literal `0.183f` used in `ackermann.c` | Derived `VMAX_REV_MS` directly from `THR_REV_RPM_CAP` and `WHEEL_RADIUS_M`. |
| 9 | Standstill pivot inner wheel rotation | Differential drove both wheels in pure Ackermann mode | Configured single-wheel pivot in `ackermann.c`: inner rear wheel held at 0 RPM, outer wheel crawls forward at ~7.5 RPM after 80% steering lock. |
| 10 | Steering pot raw min/max were placeholders (5000/25000) | Never calibrated on hardware | Measured lock-to-lock raw ADC values with a standalone ESP32 + ADS1115 rig (gain/wiring matched to STM32 firmware) and entered into `ackermann_config.h`: L 6813–15766, R 6059–14279. |
| 11 | Actuator likely to chatter at tight ±0.5° deadband | Actuator is 100%-speed bang-bang with no low-speed settle mode | Widened `STEER_DEADBAND_DEG` from 0.5° to 1.3° in `ackermann_config.h`. |
| 12 | Actuator hunting/oscillating trying to settle at zero on hardware | Confirmed on hardware: ±1.3° deadband too tight for the actuator's overshoot at 100%-speed bang-bang drive | Widened `STEER_DEADBAND_DEG` further, 1.3° → 2.5°, in `ackermann_config.h`. |
| 13 | Build failed: `ACK_STRAIGHT_DEG`, `STEER_INTEGRAL_MAX_PCT`, `KP/KI/KD_STEER` undeclared | Dropped during Phase 2 port from `STM_ackermann_backup/Inc/ackermann_config.h` into `Rover_closed_loop/Core/Inc/ackermann_config.h` | Re-added all four constants with their original backup values; project now builds 0 errors. |
| 14 | Wheels settle offset to the right at commanded zero | 2-point (min/max only) raw->angle calibration assumes both mechanical locks sit exactly at ±45° from true straight; measured raw at true straight (L=13098, R=10315) showed `angle_L`=+18.18°, `angle_R`=+1.60° instead of 0° each — a 16.6° L/R disagreement, not just an averaged offset | Added per-wheel `ANGLE_TRIM_L_DEG`/`ANGLE_TRIM_R_DEG` (18.18 / 1.60), subtracted in `_MapToAngle()` in `ads1115.c` — both wheels now independently read ~0° at true straight, not just their average. |
| 15 | Standstill pivot only crawled the outer wheel at a fixed ~7.5 RPM derived from `PIVOT_CRAWL_MS`, inner wheel fully locked at 0 RPM | Design choice from initial port | Changed to `PIVOT_OUTER_RPM`=10.0, `PIVOT_INNER_RPM`=6.0 (both wheels now roll forward — no longer a true stationary-inner pivot, a tight crawl-turn instead) in `ackermann_config.h`/`ackermann.c`. Gate on `PIVOT_LOCK_FRACTION` (80% lock before differential applies) preserved unchanged. |
| 16 | Holding steering stick at ~25-30% with no throttle snapped the wheels to full lock instead of holding ~25-30% of max angle | Standstill branch of `Ackermann_Run()` hardcoded `target_steer_deg = ±MAX_STEER_ANGLE_DEG` (snap to full lock) any time `\|Xn\| > ACK_STICK_DEADBAND` (5%) while throttle was neutral — it never used the proportional `-Xn * MAX_STEER_ANGLE_DEG` formula that the throttle-applied branch uses | Changed the standstill branch to the same proportional formula. Pivot-crawl drive still only activates once measured angle reaches 80% of lock (`PIVOT_LOCK_FRACTION`), which now only happens if the stick is genuinely held near its own extreme — moderate stick deflection just steers and holds, no drive. |
| 17 | Left potentiometer replaced — old raw calibration and zero trim invalid | Physical hardware change, not a software bug | Re-swept lock-to-lock + straight-ahead with the ESP32 rig: `ADC_L_MIN/MAX_RAW` 1920/4107, `ADC_R_MIN/MAX_RAW` 5722/12500 (right also shifted, though only the left pot was reportedly replaced — possibly disturbed during the swap). ⚠️ new left pot's span (2187) is 3.1x narrower than right's (6778) — flagged for hardware follow-up, not yet resolved. |
| 18 | Left pivot turn never achieved, even at full left lock (right pivot worked fine) | The flat-offset trim (`ANGLE_TRIM_L/R_DEG`, item 17) fixed the zero-point but was applied *before* clamping to +-45°, which silently compressed the left side's usable range: at true full left lock, computed `delta` only reached ~29.1° — short of the 36° (80% lock) needed to trigger the pivot. Right side happened to saturate at the -45° clamp early instead, masking the same underlying flaw. | Replaced the flat-trim design with a proper 3-point (piecewise-linear) calibration: `ADC_L/R_CENTER_RAW` (3500/10000) added: min->center maps to -45..0, center->max maps to 0..+45, independently per wheel. `ANGLE_TRIM_L/R_DEG` removed. Verified analytically: straight now reads exactly 0.0/0.0, full left lock reads exactly +45/+45 (delta=45, was 29.09), full right lock exactly -45/-45. Not yet re-tested on hardware. |
| 19 | Rover consistently drifts left when commanding straight, requiring manual right correction on the stick | `ACK_STRAIGHT_DEG` (1.0°, differential's "treat as straight" threshold) was narrower than `STEER_DEADBAND_DEG` (2.5°, actuator's "close enough" threshold). The actuator could legitimately rest anywhere within +-2.5° of commanded straight; any residual angle between 1.0° and 2.5° still made `Ackermann_ComputeRPM()` apply a real L/R speed differential, steering the rover toward whichever side the actuator happened to settle on. | Raised `ACK_STRAIGHT_DEG` from 1.0° to 3.0° (>= `STEER_DEADBAND_DEG`) in `ackermann_config.h`, so nothing inside the actuator's acceptable resting zone can trigger a differential. Not yet re-tested on hardware; if drift persists, next suspect is rear motor/DAC asymmetry rather than steering. |
| 20 | Needed a MANUAL/AUTO command-source select for the planned RPi autonomous link, but no free 2-position switch existed on the transmitter | `SWB` was already assigned to the reverse-speed-cap function (2-position, 60%/100%) | Repurposed `SWB` as MANUAL/AUTO select, implemented in `ibus.c`/`main.c` — see row 22; reverse-speed-cap feature dropped as a consequence (`rev_speed_pct` now fixed at `1.0f`). |
| 21 | `main.c` would fail to compile — used `IBUSData_t`, `Ackermann_Run()`, `Motor_Init()`, etc. with no `#include` for any of `ibus.h`/`ackermann.h`/`motor.h`/`encoder.h`/`ads1115.h`/`actuator.h`/`steer_pid.h`/`ackermann_config.h` anywhere in the file | A prior edit had added these includes *above* `main.c`'s `USER CODE BEGIN/END Includes` markers instead of inside them; today's CubeMX "Generate Code" (for the USART2/RPi-link peripheral) regenerated everything outside USER CODE markers from scratch, silently deleting them — exactly the regeneration risk `Rover_study.md` §10.3 warns about | Re-added all eight includes (plus `rpi_link.h`, `<math.h>`, `<stdio.h>`) inside the `USER CODE BEGIN Includes`/`END Includes` block in `main.c`, so they survive future regenerations. Not yet rebuilt (no ARM toolchain available in this environment) — needs a clean STM32CubeIDE build to confirm. |
| 22 | Needed the STM32 side of the RPi autonomous link: USART2 framing, MANUAL/AUTO arbitration, link-loss failsafe | New capability (Phase 5), not a bug | Added `rpi_link.c/h` (DMA+IDLE binary framing on USART2, mirrors `ibus.c`'s pattern for USART1); added `Ackermann_RunAuto()` to `ackermann.c/h` (bypasses joystick deadband/curve, takes RPi's absolute angle/speed targets directly); wired `main.c` to branch on `rc.auto_mode` and force `ACK_STATE_BRAKE` when AUTO is selected but `RPiCmd_t.link_ok` is false (implements the 300 ms `AUTO_UART_TIMEOUT_US` failsafe). Feedback frame (measured angle + wheel RPM + status) sent to the RPi every 20 Hz tick regardless of mode. Firmware built and flashed to the STM32; RPi side of the link not yet exercised. |
| 23 | Needed IMU heading/attitude data on the RPi5 for the autonomous guidance stack | New capability (Phase 5), not a bug | Added `RPi_companion/imu.py` (BNO055 driver via `board.I2C()` + `adafruit_bno055`, same library family as the old BBB stack, now Pi5-compatible via Blinka), `test_imu.py` (live readout sanity check), `calibrate_imu.py` (full 4-axis calibration ritual + offset dump). Old BBB calibration offsets intentionally not reused (different sensor/mounting). Software stack now deployed and verified on the actual RPi5 (see row 24-26) — only the physical sensor reconnection remains. |
| 24 | RPi5's header I2C bus (GPIO2/GPIO3) wasn't available | `dtparam=i2c_arm=on` was commented out in `/boot/firmware/config.txt` by default on this Debian 13 "trixie" image; two unrelated RP1-internal I2C buses (`i2c-13`,`i2c-14`) existed and could be mistaken for it | Uncommented `dtparam=i2c_arm=on`, rebooted. Confirmed via `i2cdetect -l`: `i2c-1` (DesignWare adapter) is the correct header bus. |
| 25 | GPIO14/GPIO15 (the STM32 UART link pins) were occupied by the Linux login console | `console=serial0,115200` in `cmdline.txt` + an auto-generated `serial-getty@ttyAMA10.service` (Pi5 numbers this UART `ttyAMA10`, not `ttyAMA0`) | Removed `console=serial0,115200` from `/boot/firmware/cmdline.txt` and disabled the getty unit — confirmed both `inactive`/`disabled` and non-regenerating after a reboot (removing the kernel parameter is what makes it permanent, not the `disable` alone). |
| 26 | `pip install -r RPi_companion/requirements.txt` failed twice building the `lgpio` wheel | Missing system (non-Python) build dependencies: first no `swig` binary (can't generate the C wrapper), then `liblgpio-dev` missing (runtime `.so` present but not the dev symlink `ld` needs for `-llgpio`) | Installed `swig` and `liblgpio-dev` via `apt-get`; install then succeeded. Documented both as prerequisites in `requirements.txt`'s header comment so a future setup doesn't rediscover this by trial. |
| 27 | `check_stm32_link.py` reported zero feedback frames received with the STM32+RPi UART physically connected | **Two stacked RPi-side causes, both confirmed via `dmesg`/`pinctrl`:** (1) onboard Bluetooth silently attached to the same UART as GPIO14/15 (`hci_uart_bcm`), leaving it at 9600 baud with the wrong line discipline; (2) the real root cause — `enable_uart=1` was never set in `config.txt`, so GPIO14/15 were never actually muxed to UART function at the hardware level (`pinctrl get 14,15` showed `none`/`none`), even though `/dev/ttyAMA10` existed as a device node and a getty had run on it previously — neither of those actually proves the pins are hardware-muxed | Added `dtoverlay=disable-bt` (disables Bluetooth on this Pi permanently) and `enable_uart=1` to `/boot/firmware/config.txt`, rebooted. Verified via `pinctrl get 14,15` → `TXD0`/`RXD0`, then via raw capture and both `check_stm32_link.py` (20.0 frames/s, 0 bad) and `read_encoders.py` (sane live data). **Link fully working end-to-end**, confirmed with the STM32 firmware unmodified — the STM32 side was correct all along (ESP32 sniffer proved this before the fix). |
| 28 | `test_imu.py` printed "board/adafruit_bno055 not available... expected off the actual Raspberry Pi" while running directly ON the Pi | User ran `python3 test_imu.py` (system Python) and `sudo python3 test_imu.py` — neither sees the packages, which only exist in `~/rover-venv` (`sudo` uses root's own `python3`, a different interpreter entirely, not the venv). The message wording didn't distinguish "wrong Python env" from "not a Pi at all", so it looked like a hardware/driver problem when it was just a missing `source ~/rover-venv/bin/activate` | Fixed the message in `imu.py` to name the actual cause and the fix (`ImportError` → venv hint; `NotImplementedError` → genuine non-Pi host, kept separate). No driver was ever needed — BNO055 does its own on-chip sensor fusion over plain I2C, already proven working. |
| 29 | `git push` failed with "could not read Username for 'https://github.com': No such device or address" right after `gh auth login` succeeded | `gh` storing a valid token in its own keyring doesn't automatically configure it as git's credential helper — a separate step | Ran `gh auth setup-git` once; `git push` worked immediately after. |
